# NSW Housing Affordability Planning Office (HAPO) — A2 Team 3 prototype

Working prototype for Assignment 2: four source systems → staging → curated → dimensional warehouse → report views → a three-use-case dashboard, plus 50 automated tests. It implements the team draft (`Assignment_2_Team_Draft.pdf`, 28 Sep) in the course Docker lab PostgreSQL 15. **All measures are synthetic.** LGA codes and names are real ASGS 2021 values, checked against the ABS correspondence file `CG_LGA_2021_LGA_2022.csv`.

Status (10 Oct 2026): a full clean build completed on the course PostgreSQL container, all **50/50 SQL tests passed**, and the dashboard export checked both synthetic golden values. The current export contains 80 UC1, 20 UC2 and 240 UC3 report rows. Build evidence is in `results/`.

## Run it

```bash
cd <your advanced-database-lab folder> && docker compose up -d   # course lab environment
bash <path to>/prototype/run_all.sh                               # reset + build + test, about 2 s
```

The package can sit in any folder. `run_all.sh` talks to the course container `student-postgres` directly; if yours has a different name, set `HAPO_PG_CONTAINER=<name>`. It creates the database `hapo_a2` automatically when it is missing, so the course database `lab` is never touched. It validates arguments before resetting the database, then runs `99_reset` and files 01–12 in order, stops at the first error, writes one SQL log per file to `results/`, and exports dashboard data from the tested reporting views. To stop early, run `bash run_all.sh --upto 07` (valid steps: 01–12).

Open `dashboard/index.html` directly in a browser for three use-case sections with four interactive charts. `dashboard/data.js` is generated by `run_all.sh`; after changing report data without a clean build, refresh it with `python3 dashboard/build_dashboard.py`. A standalone export is labelled **UNVERIFIED**. The full build uses `--verified-build`, which is refused unless the latest test run passed every test **and** the data being exported has the same fingerprint (`reporting.dashboard_fingerprint()`, recorded per run in `control.test_run`) as the data that run tested; data changed after testing therefore cannot be published as verified. The export is written to a temporary file, checked, and only then replaces `data.js`, so a failed export leaves the previous `data.js` untouched. The page displays the run ID, pass count and export time. If you view the dashboard through a local web server, hard-refresh after a rebuild (browsers may cache `data.js` and `app.js`). The exporter requires nonempty report views and unique report grains but does not fix their row counts. The full synthetic build also runs `--verify-synthetic`, which reads back `data.js` and checks Parramatta's 30.00% and 9.05-per-1,000 golden values. The four browser files can be uploaded together to a static host, including Cloudflare Pages. The dashboard is a snapshot of the tested warehouse result, not a live database connection.

`05_generate_source_data.sql` is the canonical synthetic dataset for this package (Campbelltown LGA 11500; ERP 2023–2025). Do not mix in the earlier Camden or 2026–2027 test files when assembling the final submission.

For a clean manual build, connect to `hapo_a2` (VS Code, CloudBeaver or psql), run `99_reset.sql` **first**, then files 01–06, run `06_load_or_insert_source_data.sql` **a second time**, and continue with files 07–12. The second load must close as `SKIPPED_NO_CHANGE` with zero files and rows loaded; otherwise critical test TC-LD-03 in file 11 will stop the build. Immediately after file 12, run `python3 dashboard/build_dashboard.py --verify-synthetic --verified-build` to export with the latest SQL test evidence; `--verified-build` requires that the latest test run passed every test on exactly the data being exported. Running `python3 dashboard/build_dashboard.py` by itself still exports data, but the page correctly says **UNVERIFIED EXPORT**. Run `00_environment.sql` while connected to the default `postgres` database; if its second query returns no row, run `CREATE DATABASE hapo_a2;` once, then connect to `hapo_a2`. All files are plain SQL and run in any client. File 11 collects results in the permanent table `control.test_work`, so a GUI client can run it in one go or in two parts split at the `PART 2` marker; TC-SM-03 fails if any part was skipped.

## What the data exercises

| Problem from A1 | Where it is handled |
|---|---|
| Sources name LGAs differently ("Canterbury Bankstown", "Campbelltown", "City of Sydney") | `curated.lga_alias` (reviewed aliases), file 07; 144 rows resolved by alias |
| Different formats: "LGA" prefix, thousands separators, wide month columns, DCJ suppression symbols ("s" = 30 or fewer bonds, "-" = 10 or fewer, as in the real DCJ rent tables) | Parsing functions in file 04; unpivot in file 07 |
| Different periods: quarterly, monthly, annual 30 June, Census 2021 | Day-grain `dim_time` with a financial year; UC2 summed over July–June |
| Malformed thousands separators or periods outside the supported ASGS/time range | Rejected as R03 or R02 before the warehouse load instead of being silently changed or causing a dimension lookup failure |
| Median rent cannot be re-aggregated | The source "Total / Total" row becomes the LGA headline (`is_lga_headline`) |
| Approvals are not completions | Stages reported separately; no conversion rate; no local completions |
| Traceability (UC5) | Every fact carries `source_row_id` (a foreign key to its source row) and `load_batch_id`; `reporting.vw_lineage` |
| Dirty data | 15 planted defect rows (38 rejections when housing cells are counted one by one), each rejected with a rule code R01–R07; zero rent is R03, while R07 quarantines implausible positive rents outside $50–$5,000 a week and well-formed numbers too large to store (checked on the digits before any cast, so they never abort file 07) |

**Golden values, which you can check by hand:**
- UC1, Parramatta 2025-Q1: rent 600 / income 2,000 = **30.00 %**.
- UC2, Parramatta FY2024-25: ERP rises from 260,000 to 265,200 (**+5,200, +2.00 %**). DA-approved dwellings = 12 × 200 = **2,400**, which is **9.05 per 1,000 residents**.

## Differences from the team draft (to confirm with Teams 1 and 2)

1. **Names are lower case** (`hapo_a2`, `src_rental`). PostgreSQL folds unquoted names to lower case.
2. **Added a `landing` schema.** It contains selected source-shaped extracts for the prototype, not every column or sheet in the official agency files. HAPO's lineage columns are added when rows are copied into `src_*`. File names, batch labels and `is_synthetic = TRUE` are fixed in file 06, so this build supports synthetic data only; real-data loading would require explicit delivery metadata and further validation.
3. **`rejected_row` is in `curated` only.** The draft lists it under both CONTROL and CURATED.
4. **UC1 median rule.** `dim_dwelling_type` has "All dwellings / All bedrooms" members, and the LGA headline uses the source's own total row. The draft's wording ("aggregate rent at LGA-quarter") would have combined subgroup medians.
5. **`dim_time` is at day grain and has a `financial_year`.** Each fact points at the first day of its period, or at its reference date (30 June for ERP, 10 Aug 2021 for Census).
6. **`fact_population` stores ERP only.** Annual change and growth % are calculated in the UC2 view. The draft stores them in the fact.
7. **All four facts have `source_row_id`** (the draft has it on two), and housing facts also record their `source_column`.
8. **`dim_dwelling_type` has no `source_code`.** Source spellings stay in `curated.dwelling_type_map`, so the conformed dimension carries no source-specific codes.
9. **Invalid rows run in the main build.** This means the demo shows real rejects and the reconciliation "staged = accepted + rejected".
10. **LGA alias mapping is implemented; `curated.geography_crosswalk` is reserved for future extension and remains empty.** No postcode or SA2 allocation is used.
11. **Stable surrogate keys.** Dimension keys come from the ordered business key, so a rebuild reproduces them exactly.
12. **DCJ suppression and an outlier rule (added 2 Oct, after checking the real DCJ September 2021 rent tables).** DCJ publishes the bond count as "s" when there are 30 or fewer bonds, and both the median and the count as "-" when there are 10 or fewer. `fact_rental.bond_lodgement_count` is therefore nullable, with a new flag `is_bond_count_suppressed`; Team 2, please add this to the logical model. New rule R07 quarantines medians outside $50–$5,000 a week. The idea came from the separate synthetic test package's 9999 outlier case.

The dwelling dimension keeps all 20 configured type/band members, although only nine appear in the current fixture. This fixed reference set keeps their surrogate keys stable when a later delivery omits a combination. UC2 and UC3 views also preserve an LGA-year or LGA-month with no housing facts at all: approval measures remain NULL, while reported-stage coverage is zero. The charts do not connect a line across a wholly absent month.

## Limitations (also for the report)

- All measures are synthetic. Do not read them as NSW findings.
- The core grain is LGA. Assignment 1 proposed SA2 analysis for UC1, but this prototype uses the common LGA grain of the selected sources to avoid an estimated postcode-to-SA2 allocation. No postcode or SA2 analysis is included.
- Only 2021 Census and one ASGS 2021 LGA version are supported. `valid_from`, `valid_to` and `current_flag` allow a later design extension, but this build does not implement full historical geography versioning.
- UC1 compares quarterly rent with fixed 2021 Census income. It is an area-level rental-pressure and trend proxy, not household rent burden or a measure of changing real income.
- UC2 compares annual population growth with DA approval activity. Approvals are not completions, and the units differ. The dashboard shows the nine LGAs with both FY2024–25 ERP endpoints; Cumberland's 2025 ERP is blank, and no 2026 ERP is included.
- UC3 shows lodged, DA-approved and construction-certificate-approved activity; it cannot answer whether approved projects were completed locally.
- Current facts trace to their loaded source rows and batches. Curated rows and facts are refreshed from the latest source delivery, and a clean build resets prototype schemas; past report states cannot be reproduced on demand.
- `content_md5` fingerprints the ordered rows in a landing table. It is not a checksum of an original CSV or workbook's bytes.
- Reissuing an earlier delivery is not supported. Identical content is skipped by its fingerprint and file 07 always uses the most recently *registered* file, so after deliveries A then B, re-sending A leaves B current. Supporting corrected or reissued agency files would need a separate delivery-event record that can re-activate an earlier file.
- PostgreSQL here stands in for the A1 target lakehouse. It is a medallion-style warehouse, without open file formats or time travel.
